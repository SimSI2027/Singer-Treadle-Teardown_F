# CONVENTIONS — what the reference repository does, and what this mod follows

Phase 0 of the brief: inspect `https://github.com/elvarofficial/teardown` before writing any code and bind
the build to whatever conventions it contains.

## 0. What the reference repository actually is

The repository was cloned (`git clone --depth 1`, 73 files) and every file listed. It is **not a Teardown
game mod**. It is a Claude Code *skill* named "teardown" that builds interactive 3D machine simulators as
offline HTML pages with three.js:

> `README.md`: "A Claude Code skill that turns any machine into a 3D simulator you can take apart."

File inventory (excluding `.git`):

| Kind | Files |
|---|---|
| `.xml` | **none** |
| `.lua` | **none** |
| `info.txt` | **none** |
| `.vox` | **none** |
| `README.md`, `SKILL.md`, `LICENSE` | skill docs, MIT |
| `sims/kit/*.js` | runtime, stage, HUD, easing helpers (`util.js`) |
| `sims/{v8,cessna,strandbeest}-{shared,live,film}/*.js` | 3 example machines |
| `sims/build.mjs`, `capture.mjs`, `sfx/*.py` | bundler, frame capture, procedural sound |

Because there is no Teardown content, every *engine-level* question below is answered
**NOT FOUND — using fallback**. The repository does, however, encode strong conventions for *exactly the
kind of thing this mod is*: an interactive take-apart machine exhibit with one button per subsystem. Those
conventions are adopted wherever they translate to Teardown, and each is quoted with its source.

Engine facts the fallbacks rely on were checked against the official modding pages
(`https://teardowngame.com/modding/`, `.../modding/api.html`) and the official palette file
(`.../modding/downloadable/teardown_palette.vox`). Where even those were silent, the assumption is listed in
§12 "Unverified engine assumptions".

## 1. Object construction (`<vox>` vs `<voxbox>`, scale, materials)

**Reference repo: NOT FOUND — using fallback.** The repo builds geometry from code (`sims/v8-shared/engine.js`
lathes parts; `SKILL.md`: "The geometry, built from code: lathed parts, tubes, instanced links").

**Adopted from the repo, translated:** *geometry is generated by code from real dimensions, never hand-placed.*
`SKILL.md` rule 2: "Real numbers, one source. Get the real dimensions first … Every gauge, chart and label reads
from the same function that poses the parts." This mod therefore generates every voxel with
`tools/generate.py` from a dimension block, and the same generator writes the Teardown `.vox` files, the
`prefab.xml`, and the web viewer's geometry, so the game and the website cannot disagree.

**Fallback chosen:**

- `.vox` files written programmatically (MagicaVoxel format, one model per file), placed with
  `<vox file="MOD/vox/<name>.vox" pos="…" scale="0.1"/>`. **Scale 0.1 ⇒ 1 voxel = 1 cm**, ten times finer
  than the engine default of 0.1 m, which is what a 2 mm-thick needle bar or a thread path needs. `<voxbox>`
  is rejected: the docs show it only at the default 10 cm resolution (`Spawn("<voxbox size='10 10 10' …/>")`),
  which cannot draw a sewing machine.
- Materials come from palette index ranges. The official docs say only that "an object made of colors in the
  wood group (indices 57 - 72) will still be wood". The official material table lists, in order, *Glass, Grass,
  Dirt, Plastic, Wood, Plaster, Concrete, Brick, Weak Metal, Hard Masonry, Hard Metal, Heavy Metal, Rock*.
  With glass taking 8 slots and every other group 16 slots, Wood lands exactly on 57–72. That anchors the
  inferred layout used here:

  | Material | Indices | Hardness (official) | Used for |
  |---|---|---|---|
  | Heavy Metal | 169–184 | Unbreakable | iron castings, steel, nickel, brass |
  | Rock | 185–200 | Unbreakable | oak, leather, rubber, thread, felt (coloured to look right) |

  Only the two **unbreakable** groups are used, which makes the whole exhibit non-destructible and
  non-flammable in normal play. Oak drawn with rock voxels sounds stony when struck; see Deviations.

## 2. Hierarchy (`<prefab>/<group>/<body>/<shape>`, naming, anchors, `<instance>`)

**Reference repo: NOT FOUND — using fallback.** The repo's analogue is the one-folder-per-machine split
(`SKILL.md` "How a machine is built": math / geometry / stage / console / live), which maps onto:
generator (geometry) → `prefab.xml` (stage) → `exhibit.lua` (console + live).

**Fallback chosen:** the hierarchy from the brief §2.2, with names `sys_<id>`, groups `machine`, `console`,
`display`, and three `<location>` anchors. `<instance>` is not used (nothing is repeated across files).

## 3. Joints

**Reference repo: NOT FOUND — using fallback.** The repo has no physics at all; every pose is a function
(`SKILL.md` rule 3: "One input drives everything … Nothing is keyframed by hand").

**Fallback chosen:** **no joints anywhere.** Articulation *inside* a subsystem (drawers sliding out, the
gear train exploding, the band wheel spinning) is done with `SetShapeLocalTransform` on shapes of the same
static body, driven by the same deterministic clock. This is stricter than the brief allows and removes
every source of physics drift.

## 4. Grouping and tagging

**Reference repo: NOT FOUND — using fallback.** The repo's analogue is a single table of subsystem keys that
drives buttons and isolation (`sims/v8-shared/live.js:104`:
`const ov = {callouts: 1, charge: 1, arrows: 1, isolate: 0, refract: 1, charts: 1};`).

**Fallback chosen:** tags `exhibit`, `sys=<id>`, `btn=<id>`, `anchor=<role>`, `art=<id>` (articulated
shape). Scripts find bodies with `FindBodies("sys", false)` and read `GetTagValue(h, "sys")` **once in
`init()`**. Scope (official docs): "Functions that allows scripts to 'find' objects will by default only
return objects matching the search criteria below the script in the hierarchy." So the `<script>` element
**wraps** the exhibit (see Deviations), and two spawned exhibits never control each other.

## 5. Voxel usage and budgets

**Reference repo: NOT FOUND — using fallback.** The closest rule is a size budget for the page
(`SKILL.md`: "Keep the page under 1 MB").

**Fallback chosen:** 1 cm voxels everywhere, hollow castings (1–2 cm walls), lattice frames cut with real
openings. Budgets from the brief: ≤ 20 bodies, ≤ 180 shapes, ≤ 250 k voxels, ≤ 30 shapes per body.
`tools/generate.py` counts and **fails the build** if any budget is exceeded.

## 6. Performance

**Reference repo, adopted:** "Test on an integrated GPU" and quality tiers (`SKILL.md` "Live page rules").
In Teardown terms, the per-tick cost is kept flat: one `QueryRaycast`, cached handles, no tag parsing and no
`Find*` calls after `init()`, `SetBodyTransform` only on bodies that are moving this tick.

**Fallback chosen:** all bodies `dynamic="false"`, no lights except two warm spots, no particles, no
ropes, two sounds.

## 7. Separation animation

**Reference repo, adopted (this is the core convention):**

- *Pure function of time.* `sims/kit/util.js:1`: "Everything animated must be a pure function of `t`
  (seconds) so live playback and frame capture match." `SKILL.md` "render(t) contract": "no `Math.random` …
  no `Date`, no state carried between frames." → `exhibit.lua` computes every pose with
  `pose(id, t)` from an accumulated `dt` clock; closing evaluates the *same* function with `t` running
  backwards, then snaps to the stored home transforms.
- *Easing vocabulary.* `sims/kit/util.js:6–14` defines `smooth` (smoothstep) and `easeInOutCubic`, and
  `prog(t, t0, t1, ease)` "0..1 progress of t between t0 and t1, eased". The Lua port uses the same three
  functions with the same names and formulas.
- *Toggle with eased progress.* `sims/cessna-shared/live.js:105`:
  `const eased = (k, dur = 0.7) => { … return d.on ? x : 1 - x; }`; i.e. one state flag, one duration,
  progress derived from time since the flip. That is the OPENING/CLOSING pattern used here.
- *Fix collisions with a number.* `SKILL.md` rule 7: "When a part pokes through another, scale or move it in
  the parameter block. Never hide it with the camera." → each subsystem has an `exit` vector in
  `SUBSYSTEMS`; `tools/check_paths.py` checks voxel-exact interpenetration along the real animated path, and
  exits are tuned by number until the check passes.

**Fallback chosen (engine level):** static bodies moved with `SetBodyTransform` every tick while moving.
Never `SetBodyVelocity`, `Explosion`, `MakeHole`, `Shoot`, `Paint`.

## 8. Interaction design

**Reference repo, adopted:**

- *A button for every subsystem* (`SKILL.md` description: "a button for every subsystem"; `README.md`: "a
  button opens the part doing the work").
- *One accent, and it means something.* `SKILL.md` "Taste, with numbers": "One accent, and it means
  something: the part that is working right now." → only the button of the subsystem in motion or on show
  glows (`SetShapeEmissiveScale`); hovering draws an outline, never a second glow colour.
- *Nothing dead-still.* `SKILL.md`: "one element always alive." → the showcased subsystem sways slowly
  (`12° · sin(0.6 t)`).
- *Timing.* `SKILL.md` checklist: "Each state holds long enough to read: 1 s for a short phrase plus 0.25 s
  per word beyond three." → the info panel fades in only after the subsystem has arrived.

**Fallback chosen (engine level):** raycast from `GetPlayerCameraTransform()` with `QueryRaycast` (2.5 m),
reject non-button shapes via a handle→id lookup table, `DrawShapeOutline` on hover, `UiText` prompt
"[E] Inspect: <name>", `InputPressed("interact")` to fire. Sounds via `LoadSound`/`PlaySound` with two
procedurally synthesised `.ogg` files (see §10).

## 9. Subsystem separation and exclusivity

**Reference repo, adopted:** isolation is exclusive: `sims/v8-shared/live.js:133`:
`ov.isolate = view === 'cyl' ? 1 : 0;`: one thing is isolated at a time.

**Fallback chosen:** one body per subsystem; a state machine with a one-slot queue enforces "one open at a
time" (press B while A is shown → A closes fully, then B opens).

## 10. Sound

**Reference repo, adopted:** `SKILL.md` "Sound": "`sfx/` synthesises every sound in pure Python …
reproducible", and "Accent, never narrate: continuous motion stays silent." → `tools/make_sounds.py`
synthesises a brass *click* and a soft mechanical *slide* deterministically (fixed seed); no sound plays during
continuous motion such as the sway or RUN.

## 11. Mod packaging

**Reference repo: NOT FOUND — using fallback**, verified against the official modding page:

## 12. Unverified engine assumptions

These could not be confirmed from any official text; each is isolated so a wrong guess has a contained effect.

| Assumption | Where it matters | Containment |
|---|---|---|
| A `<vox>` shape's pivot is the centre of the model's bottom face | where shapes land | every shape's grid is generated **symmetric about its own pos** in x and z, so a mirrored axis only flips a part in place and never moves it |
| MagicaVoxel Z is Teardown up (Y); MV X → TD X; MV Y → TD −Z | orientation | same as above |
| `scale="0.1"` is honoured on `<vox>` | voxel size | `GetShapeSize` (official) reports the voxel size; the README says what to change if needed |
| Palette layout of §1 beyond Wood 57–72 | destructibility/sound only | colours come from the RGBA chunk regardless, so visuals are unaffected |
| `SetBodyTransform` moves static bodies | animation | widely used for moving static platforms; this is the brief's own fallback |
| MATL `_emit` entries make `SetShapeEmissiveScale` visible | button glow | hover/active buttons are also outlined with `DrawShapeOutline`, so feedback never depends on emission alone |

## Deviations

1. **`<script>` wraps the exhibit** instead of being a self-closed sibling. Official scoping rule (§4): finds
   only see objects *below* the script. Wrapping makes `FindBodies(…, false)` see exactly this exhibit, so
   several can be spawned side by side.
2. **No joints at all**, even inside subsystems (brief permits decorative ones). Shape-level articulation is
   deterministic and cannot drift.
3. **Wood-, leather- and rubber-looking parts use the Rock material range.** The brief requires
   non-flammable, non-destructible materials; Teardown's Wood is soft and burns.
4. **Shift vector is (−0.80, 0, −0.30) m** (left and back), not a pure 0.6 m to the left: the needle end of
   the head sits at x ≈ −0.17 m and needs the cabinet to clear it completely, and the backward component lets
   forward-exiting parts clear the table edge. Verified by `tools/check_paths.py`.
5. **Per-subsystem `exit` vectors replace the uniform "lift 8–12 cm up"** for nested parts (drawers slide
   out forward, the shuttle drops out of its race, the treadle slides forward out of the stand). Lifting a
   drawer straight up would drive it through the table top. Top-mounted parts still lift 10 cm up.
6. **Interpretation of subsystem contents**: see `docs/PLAN.md` §1 "Interpretation notes" (where the
   Ø 0.30 m band wheel and the stand crank live).
